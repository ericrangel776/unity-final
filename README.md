# Deck-Builder ARPG (vertical slice)

A real-time action RPG where every attack is a card. You fight with a 3-card hand. Cards clash with enemy cards
mid-air, and the higher value breaks the lower one. You stock three cards into a *Sleight* combo, and reload under
pressure with a timing minigame. Runs are short roguelike floors: pick a door (Map Card), clear the room, draft a card,
repeat, then fight a boss with a visible 15-card deck.

The game was built as a class final project and is scoped as a **vertical slice**: one floor, six rooms, four room
families, six relics and one boss. All names and assets are original. The design doc is
[`docs/design/game-design-doc.md`](docs/design/game-design-doc.md).

## Quick start

**Requirements:** Unity **6000.3.24f1** (6.3 LTS), via Unity Hub. The project uses URP 17.3, Input System 1.20 (legacy
input is off), Cinemachine 3.1.7, uGUI and Test Framework 1.6. No other packages or assets are needed.

1. Unity Hub -> **Add** -> select this folder. The first import takes several minutes (shader compilation).
2. Open `Assets/_Project/Scenes/M3_Run.unity` (the full run) or `M1_Arena.unity` (one dummy, for testing combat).
3. Press Play. **Ctrl+Shift+B** (`DeckArpg/Play Boss Fight`) jumps straight to the boss.

### Controls

| Input | Action |
|---|---|
| WASD / mouse | Move / aim |
| 1, 2, 3 | Play that hand card (it fires, then the next card is drawn) |
| Q | Parry with the reserved `0` card (play it *after* the enemy swings) |
| Left mouse | Value-1 poke (always available) |
| Space | Dash (i-frames) |
| Shift + 1/2/3/Q | Stock a card into the Sleight (the 3rd card fires it) |
| R, then R again | Reload. Press again in the sweet spot for an instant reload and a speed boost |
| Shift + R | Overburn reload: pay HP to get burned cards back |
| F1 or ` | Debug menu (Editor and Development builds) |

## Project layout

```
Assets/_Project/          all our code and content, kept apart from template/third-party assets
  Scripts/Core/           DeckArpg.Core      rules and data: cards, clashes, Sleights, rooms, relics (no scene code)
  Scripts/Gameplay/       DeckArpg.Gameplay  MonoBehaviours: player, enemies, boss, hitboxes, FX, run director
  Scripts/UI/             DeckArpg.UI        HUD, run screens, debug menu (all built in code)
  Scripts/Editor/         DeckArpg.Editor    builders that generate the scenes, prefabs and card assets
  Tests/EditMode/         rules tests (fast, no scene)
  Tests/PlayMode/         scene tests, screenshot capture, bot measurements
  Scenes/  Prefabs/  ScriptableObjects/Cards/  Art/Materials/
docs/design/              game design doc (the source of truth)
docs/specs/               one spec per feature, written before it was built
```

### Assemblies and the dependency rule

| Assembly | References | Why |
|---|---|---|
| `DeckArpg.Core` | nothing of ours | Pure rules, so they can be unit-tested without a scene |
| `DeckArpg.Gameplay` | Core, Input System, Cinemachine, URP | Turns rules into behaviour in the world |
| `DeckArpg.UI` | Core, Gameplay, uGUI, Input System | Shows state and never owns rules |
| `DeckArpg.Editor` | Core, Gameplay, UI, Cinemachine | Editor-only content builders |
| `DeckArpg.Tests.*` | Core, Gameplay, UI (plus Input System / Cinemachine / URP as needed) | NUnit; `InternalsVisibleTo` lets tests reach `internal` hooks |

Dependencies only point one way: **Core <- Gameplay <- UI**. The asmdefs enforce it, because Gameplay can't even see
UI types. The namespace always matches the assembly name.

### Content is generated by code

The scenes, prefabs and card assets are built by editor scripts under the `DeckArpg/` menu (`Build Starter Cards`,
`Build Run Content`, `Build M1 Arena`, `Build M3 Run Scene`, `Apply Build Scene Order`). Re-running a builder
**overwrites** what it generates, so change the builder, not the asset. Build order: `M3_Run` first, then `M1_Arena`.

## Testing

Close the Editor first (a project can only be open once), then from Git Bash at the repo root:

```bash
"/c/Program Files/Unity/Hub/Editor/6000.3.24f1/Editor/Unity.exe" -batchmode -nographics -projectPath "$(pwd -W)" \
  -runTests -testPlatform EditMode -testResults "$(pwd -W)/TestResults/editmode.xml" -logFile "$(pwd -W)/TestResults/editmode.log"
```

Use `-testPlatform PlayMode` (and `playmode.*` file names) for the scene tests. Exit code 0 means everything passed. The
totals are in the `<test-run ...>` line of the XML, and compile errors show as `error CS` lines in the log. Current
suite: about 1,000 EditMode tests and about 490 PlayMode tests.

A few PlayMode fixtures are `[Explicit]` and only run when named with `-testFilter`:
- `HudScreenshotCapture` renders the HUD to `TestResults/screens/`. Run it without `-nographics`.
- `BossFightMeasurement` and `RunTimingMeasurement` let a scripted bot play the boss or a whole run and report pacing.

The **debug menu** (F1) can force any room, clear or skip waves, toggle god mode, spawn enemy variants, apply statuses,
and slow or pause time. Each feature adds its test hook as one `DebugCommand` row in `Scripts/UI/Debug/DebugCommands.cs`.
A smoke test runs every row.

## Design decisions and why

Each decision below lists what was chosen, why, and what it costs.

**Rules live in a pure Core assembly.** Clash resolution, Sleight composition, Active Reload, room intensity, rewards
and relics are plain C# with no `MonoBehaviour`. *Why:* the rules are the riskiest part of a card game, and EditMode
tests run them in milliseconds with no scene. *Cost:* Gameplay needs a thin adapter for each system (for example
`ElementStatusEffects` around the Core `ElementStatusState`).

**`CardData` is a read-only ScriptableObject; run state lives in `RuntimeCardInstance`.** Upgrades, Premium status and
room buffs are fields on the runtime instance, and `GetEffectiveValue()` clamps the result to `[1, 9]`. *Why:* a
ScriptableObject changed in Play mode stays changed in the Editor, which would corrupt the authored card pool between
runs. *Cost:* every "what is this card worth" question goes through the instance, never the asset.

**`0` is a flag, never a number.** The Zero-Breaker card has `isZeroBreaker` set and is never part of value maths, so
sums and multipliers can't produce a 0 by accident. It breaks any card only when played *second*, judged by a strictly
greater activation tick. A tie bounces.

**Every hitbox carries an immutable `AttackPayload` snapshot taken when it spawns.** *Why:* a card can be upgraded,
burned or discarded while its projectile is still flying. A snapshot means the hit resolves with the values that were
true when it was played.

**Body hits wait for the windup; clashes resolve first.** Hitboxes register body contacts in trigger callbacks but deal
damage only from `FixedUpdate` after a short windup. *Why:* Unity calls trigger callbacks in an arbitrary order. Waiting
one step guarantees that a card-vs-card clash cancels an attack before it can also land, and it opens the window in
which a late `0` can still parry.

**Local clashes for mobs, a global HUD clash only for Boss and Elite Sleights.** *Why:* resolving every mob clash in a
big HUD moment would stop the action several times a second. Only the boss's big attacks earn that spotlight.

**One owner for `Time.timeScale` (`HitStop`).** Hit-stop, the Deadlock minigame and the debug slow-mo all go through it.
*Why:* `Time.timeScale` is global. Two systems saving and restoring it independently can save `0` as the "previous"
value and leave the game frozen. Hit-stop waits use `WaitForSecondsRealtime`, and inputs are buffered for 0.2 s on
unscaled time, so a press during a freeze isn't lost.

**Safeguards against unwinnable states.** The *Floor of 3* stops Sleights from burning cards when the deck is down to
3. A value-1 poke and an i-frame dash are always available. Overburn trades HP for burned cards. Milling the boss's
visible deck to 0 staggers it for 4 s. *Why:* deck-builders can soft-lock a player who built badly. Each rule closes
one of those holes.

**UI is built in code with uGUI `Text`.** It uses no prefabs and no TextMeshPro. Each HUD element creates its own
canvas in `Awake` (`UiFactory`). *Why:* greybox UI changes constantly. Code diffs review cleanly, while prefab YAML
doesn't, and separate canvases mean a changing damage number doesn't rebuild the hand HUD. Views rebuild a string only
when the values it shows change, so per-frame HUD updates don't allocate. *Cost:* no visual layout editing. Switch to
TMP and prefabs when real UI art arrives.

**Procedural audio and runtime-built FX.** SFX are synthesised (`SfxSynth`), and particle systems, materials and
textures are created at runtime (`ParticleFx`, `FxShapes`). *Why:* the project needs no imported art or audio, which
keeps the repo small. Shared materials are cached so nothing leaks per scene load. Body tints (hit flash, statuses,
variants) go through one `MaterialPropertyBlock` owner (`BodyTint`), so effects never edit shared materials and never
fight each other.

**Hitboxes are created per attack, not pooled.** This was considered during the refactor and deliberately left alone.
Several systems keep references to an attack's hitboxes (the boss's live-Sleight list, tests). With pooling, a cancelled
hitbox could be reused for a different attack and be mistaken for the old one. At a few attacks per second the
allocation is negligible, so the simpler lifetime wins.

**Spec -> branch -> PR for every feature.** Each system has a spec in `docs/specs/`, written before the code, and its
own branch and PR with tests. *Why:* it keeps a solo project reviewable, and each spec records the tuning decisions and
playtest feedback behind the numbers.
